# Repository review, 2026-10-16

Scope: project-owned C++/CUDA kernels, Matrix/ISA utilities, tests,
benchmarks and experiments, CMake/CI configuration, guides, four articles,
chart inputs and generated SVGs. Fetched third-party implementations are
reference dependencies, not part of this code review. Concurrent article
edits, historical-data additions and the new SME block-sweep experiment in
the workspace were retained. `include/hpc/lowp.hpp` appeared later during
the review; it is ongoing low-precision work and is outside the correctness
and performance results below. The design guide describes that distinction.

The new [file-by-file design guide](kernel-design.md) explains each kernel's
purpose, loop order, packing and register layouts, tails, precision and
tradeoffs, plus the supporting files. Historical benchmark tables remain
historical measurements; this review does not relabel them as fresh runs.

## Correctness and maintainability changes

- Matrix checks dimension multiplication, byte multiplication and alignment
  rounding before allocation. Empty copies avoid null memcpy arguments;
  moved-from matrices become empty and remain safe to fill or clear.
  Over-aligned element types are rejected explicitly.
- Zero scalar tile sizes now fail at compile time instead of looping forever.
  AVX2 availability also requires FMA. ISA comments distinguish testing a
  numeric macro from testing whether its name exists.
- CUDA Matrix wrappers check shape assertions and 32-bit indexing limits.
  Empty products bypass invalid allocations/launches; zero K overwrites C
  with zeros. Device entry points enforce the corresponding empty-product
  behavior. Raw pipelined WMMA rejects invalid tile shapes.
- CUDA capability queries follow the selected device. cuBLAS retains its
  existing single-host-thread, fixed-device handle contract; switching or
  resetting that device after first use remains unsupported. A proposed
  per-device cache was removed after the tiny-case performance check.
- WMMA shared bases explicitly have 32-byte alignment. The raw-MMA kernel
  shares WMMA's implementation when compiled below sm_80, fixing the empty
  body that older PTX could otherwise execute when JIT-loaded on a newer GPU.
- CUDA events and benchmark buffers clean up on exceptions. The redundant
  device C memset was removed: all kernels overwrite their output.
- SVE and SME inactive edge transfers avoid constructing out-of-allocation
  pointers. SME retains a separate inlined full-tile transfer path.
- Accelerate rejects dimensions outside its int interface. FMOPA experiments
  explicitly initialize ZA. The SME configure probe exercises both vectors
  of an SME2 load and FP32/FP64 outer products, and observes the result.
- Optional GNU-assembly CPU experiments are excluded under MSVC, and AVX-512
  C++ flags no longer leak into nvcc invocations.

The hand-unrolled SIMD micro-kernels and tile sizes were kept. Their
repetition expresses register allocation and ISA differences; replacing
those loops with a generic abstraction without evidence would risk codegen.

## Documentation corrections

Descriptions now distinguish compile-time CPU targeting from runtime GPU
selection, FP16 input rounding from an output error bound, and prefetch
locality hints from guaranteed cache placement. CUDA levels 3 and 4 are
separate extensions of level 2. A 16x16 block gives a warp two 16-thread
rows, not a single 32-column row. Event intervals can include GPU idle time
while the host submits work, especially for tiny kernels.

The GPU rate calculation is about 251 FP32 FLOPs per SM per cycle, not 126
(`59.7e12 / (84 * 2.83e9)`). The measured legacy MMA path is not a universal
ceiling for all Blackwell Tensor Core APIs. Padding B by 32 float columns
at N=4096 increases storage and the total page footprint by about 0.8%; it
does not leave the page count exactly unchanged. Cache-set indexing and
matrix-unit sharing on M4 remain interpretations of controlled experiments,
not documented physical mappings. Build instructions clarify optional
compiler support, native/headless CUDA targets and MSVC x64 assumptions.

## Performance evidence and limits

The [review data](experiments/review-20261016/README.md) records measured
before/after durations and variability. Before binaries were saved before
editing; the runtime-size Mac comparison additionally loads two separately
compiled source snapshots into one process with distinct namespaces.

Performance verification is bounded by the tested hardware, shapes, compiler
and machine load. It is not a guarantee for SVE, MSVC, another GPU or every
possible rectangular shape. The original article measurements are not
substitutes for before/after measurements of these changes.

| Comparison | Observed result |
|---|---|
| 26 custom CUDA cases at N=4096/8192 | Speedup range 0.9964–1.0045; median 0.9999 (within about ±0.5%) |
| 48 Linux CPU cases at N=256/1024 | Median speedup 1.0002; individual ratios 0.961–1.031 |
| Tiny cuBLAS FP16, N=256, final paired check | Before 5.507–5.608 µs; after 5.592–5.646 µs. Adjacent differences 0.04–0.08 µs, within baseline variability |
| Mac paired runs | Desktop load still caused large changes in unchanged paths; inconclusive as a blanket no-regression check |
| Mac same-buffer FP64 SME, N=1024 | One-tile ratio 1.009; macro-kernel ratio 0.970, with substantial per-pair variability |

Thus there is strong evidence of unchanged large custom CUDA performance,
but **a zero-regression claim for every kernel and shape is not established**.
Small launch-level timing uncertainty and load-sensitive Mac results remain explicit
limitations. The data and reproduction harness are retained so they can be
checked on an idle machine; the unfavorable measurements are not discarded.
